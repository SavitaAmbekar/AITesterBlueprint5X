1. Objective & overview

Validate that the VWO login experience provides secure, reliable, accessible, and responsive access to the VWO platform, with clear recovery paths and enterprise authentication options.

Product under test

VWO Login Dashboard, identified in the PRD as the entry point at app.vwo.com, including authentication and related user-facing flows.

Target users

Digital marketers, product managers, UX designers, developers, enterprise teams, CRO specialists, and data analysts.

Quality objectives

Validate core and enterprise login journeys, minimize login friction, protect account and session data, and maintain the PRD's usability and performance goals.

Success measures from PRD

Login success rate target of 95% or higher; login-page load under 2 seconds on standard connections; user satisfaction target of 90% or higher; 99.9% availability target.

2. Scope

In scope

  • Email/password authentication, input validation, authentication errors, loading feedback, and successful transition to the VWO dashboard.
  • Remember Me behavior, session handling and timeout behavior, and preservation of the returning user's context where supported.
  • Password visibility/entry behavior if provided by the implementation; password strength/requirements feedback; forgot-password, email recovery, and reset-token flow.
  • Optional multi-factor authentication; enterprise SSO (including SAML/OAuth as specified); and optional Google/Microsoft or other configured social identity providers.
  • New-user trial/signup navigation, VWO branding, product announcement, and Light/Dark Mode options identified in the PRD.
  • Responsive behavior, keyboard navigation, screen-reader support, high-contrast behavior, WCAG 2.1 AA review, and cross-browser/device compatibility.
  • HTTPS enforcement, secure authentication/session handling, rate limiting, privacy/compliance behavior, and security-event/audit expectations.
  • Login page performance, concurrent login capacity, availability monitoring, login analytics, and support-assistance paths.
  • Smoke, sanity, functional, integration, end-to-end, regression, usability, exploratory, performance, and security validation.

Out of scope or deferred

  • Full VWO experimentation, personalization, and analytics feature testing after login, except validating the authenticated handoff and dashboard landing.
  • Full trial registration/onboarding behavior after navigating away from the login experience; validate the link/entry handoff only unless scope is expanded.
  • Biometric authentication, adaptive/risk-based authentication, and PWA behavior are listed as future enhancements in the PRD and are deferred until confirmed for this release.
  • Penetration testing of production systems is not authorized by this plan. Security tests must use an approved non-production environment and approved test accounts.

5. Test strategy

  1. Requirements analysis and traceability: review the approved PRD and resolve TBDs; map each requirement to scenario IDs and acceptance evidence.
  2. Test design: create prioritized cases using equivalence partitioning, boundary-value analysis, decision tables, state-transition testing, use-case testing, error guessing, and exploratory testing.
  3. Shift-left and smoke: review authentication, privacy, accessibility, and integration design early. For each candidate build, perform smoke checks for page availability, essential form behavior, and the primary login route.
  4. Stable-build execution: after smoke passes, execute prioritized functional and negative cases, then integration, end-to-end, accessibility, compatibility, and non-functional coverage.
  5. Security validation: validate expected protections and observable outcomes using approved test accounts and controlled QA/pre-production tests. Do not execute unauthorized attacks or production load tests.
  6. Defect and retest cycle: log defects with reproducible evidence, triage by severity/priority, retest fixes, and run regression for affected flows. Repeat cycles until exit criteria are met.
  7. Parallel execution: multiple test resources may execute across supported environments in parallel once environment, account, and test-data ownership is agreed.

Test levels and evidence

  • Functional/UI: field behavior, navigation, visible states, session choices, and error recovery.
  • Integration/E2E: identity providers, recovery email/token flow, analytics events, and authenticated dashboard handoff.
  • Non-functional: performance, controlled concurrency, accessibility, compatibility, security controls, and availability/monitoring evidence.
  • Evidence: case result, environment/build, sanitized screenshots or logs, timestamps, and linked defect IDs. Never attach plaintext passwords, tokens, or personal data.

6. Entry, exit & execution criteria

Requirements analysis

Entry

PRD and available design/technical details are shared with QA.

Exit

Requirements are reviewed, testable acceptance criteria are identified, TBDs and questions are recorded, and scope is agreed.

Test design and environment readiness

Entry

Requirements have been reviewed and the target release scope is known.

Exit

Prioritized scenarios/cases are reviewed; test URLs, accounts, provider integrations, access, and evidence handling are ready.

Test execution

Entry

Candidate application is available; smoke test passes; test cases and environment are ready; test accounts and test data are authorized.

Exit

Planned cases have results; P0/P1 failures are resolved or formally accepted; defects are logged and retested; required performance/accessibility/security evidence is reviewed; no unresolved release-blocking issue remains.

Test closure

Entry

Execution exit criteria are met and test/defect results are available.

Exit

Test summary, coverage, residual risks, open defects, and approvals are documented and shared with stakeholders.

Release quality gate. The PRD's numeric targets must be evaluated using agreed measurement definitions and a representative environment. Release sign-off requires no open P0 defects, documented disposition of remaining defects, and approval of any unmet or unmeasurable target.

8. Defect reporting procedure

Use JIRA as the defect-tracking tool identified by the supplied skill template; confirm the project/board and workflow before execution.

  1. Record a concise title, affected requirement/scenario ID, build/environment/browser, prerequisites, sanitized test account type, and reproducible steps.
  2. Include expected versus actual result, severity, priority, occurrence frequency, and safe evidence (screenshots/logs with secrets and personal data removed).
  3. Triage with product, QA, and engineering; assign an owner and target fix/retest cycle. Reopen if the issue persists.
  4. Share a daily status summary during active test execution, including new, open, fixed, blocked, and retested defects.
